# V5 C57 reconstruction

Input:

`The signed result is -204, not 204.`

V5 starts from V3 tokens and adds bare numeric matches that are not already
occupied. Because the local extractor did not own the leading sign, V5
emitted a `NUMBER` occurrence for the inner substring `204` in `-204` and a
second `NUMBER` occurrence for the later standalone `204`. Both had the same
normalized value. V5's sibling/polarity logic could classify the later value
as rejected and its length-preserving mask then removed the wrong numeric
identity from the subsequent V3 re-extraction context.

The first identity loss is **EXTRACTION**: the sign-bearing lexical extent was
not owned by the occurrence. The downstream failure is a
`NESTED_LITERAL_COLLISION` / `SPAN_IDENTITY_LOSS`, not a V3 comparison change.
The later V6 fix correctly moved sign ownership into the span and removed the
nested candidate, but did not introduce a persistent ledger or remove the
mask/re-extract boundary.
